## 一、Agent 评估 vs 传统行业评估

### 1.1 从 TDD 到 EDD

**核心观点：** 在传统软件工程中，我们靠 **TDD（Test-Driven Development，测试驱动开发）** 保证质量——先写测试用例，再写实现，红→绿→重构。因为传统软件是**确定性系统**：相同输入必然产生相同输出，测试断言可以写死 `assertEqual(expected, actual)`。

但 Agent / LLM 系统是**概率性系统**：相同输入可能产生不同输出，且输出是自然语言、代码、多步轨迹等**开放形态**，无法用一个精确等值断言来覆盖。于是评估范式从 TDD 演进到 **EDD（Evaluation-Driven Development，评估驱动开发）**。

**TDD vs EDD 对比：**

| 维度         | TDD（传统软件）              | EDD（Agent/LLM 系统）                   |
| ------------ | ---------------------------- | --------------------------------------- |
| 系统性质     | 确定性                       | 概率性                                  |
| 断言方式     | 精确等值（pass/fail）        | 打分/相似度/裁判（分布式、区间）        |
| 输出形态     | 结构化、可枚举               | 自然语言、代码、多步轨迹                |
| 通过标准     | 100% 通过                    | 达到目标分数/阈值（如 ≥ 0.85）          |
| 回归方式     | 单测/集成测试                | 评估集（eval set）+ 持续跑分            |
| 关注点       | 功能正确                     | 正确性 + 轨迹 + 成本 + 安全 + 稳定性    |

> **【面试卡片】Q1：TDD 你了解过吗？你自己用 TDD 做过完整开发吗？**
> （202606 社招·雄帝科技 Agent 二面题目）

**✅ 优秀回答范例：**

TDD 我了解，也实践过。传统 TDD 就是**测试先行**：先写测试用例让它失败，再写最小代码让它通过，然后重构，靠测试来驱动设计，而不是"写完再补测试"。

不过在 Agent 项目里没法直接照搬——因为大模型是**概率性**的、输出又是**开放式**的，同一个输入跑两次结果都可能不一样，没法像传统代码那样断言"输出等于期望值"。所以我用的是它在 Agent 时代的升级版——**评估驱动开发（EDD）**。EDD 的内核和 TDD 一样：动手之前先把"怎么算成功"定义清楚，再用一套**可量化、可重复的评估**来驱动每次改动，只是把"断言相等"换成了打分、相似度、通过率这类度量。

**具体落地，我顺着三个阶段做（呼应本文全景图）：**
1. **模型确定（选型期）**：先选对基座模型——用成本、延迟、隐私这些硬约束把候选缩小，再用**业务私有数据集**做筛选，避免公开榜单的数据污染带偏（详见 3.2）。
2. **开发阶段（上线前）**：这一段最能体现 TDD 思想——先把各环节"怎么评估"定义清楚，再去搭 Pipeline。先做**组件级评测**，把 Prompt、RAG、工具调用、规划推理各自的失败模式逐个测出来；再做**集成级评测**，用端到端成功率、轨迹评测、多轮对抗、多 Agent 协作验证整机能不能稳定完成任务；等这些维度的测法和指标都定清楚了，再把评测集和评估 Pipeline 组装起来，并设一道**发布闸门**，质量、延迟、成本、安全都达标才能上线（详见 3.3–3.5）。
3. **上线阶段（上线后）**：把同一组指标搬到真实流量里持续监控，做 A/B 灰度、盯漂移和成本安全告警，一旦发现新问题就**回灌评测集重新跑回归**（详见 3.6）。

**💡 一句话总结：** TDD 依赖"确定性"这一前提，Agent 因输出不确定无法用等值断言，所以升级为 EDD——用"评估集 + 打分器"替代"测试 + 断言"来驱动整个研发闭环。

### 1.2 Agent 评估和传统评估的不同

> **【面试卡片】Q2：你觉得 Agent 行业的测试和传统行业有哪些不同？**

**✅ 优秀回答范例：**

核心一句话：**Agent 打破了传统测试赖以成立的前提**。传统软件测试那一套之所以不能直接拿来测 Agent，是因为 Agent 在"确定性"这个根基上就变了。我一般从**五个维度**讲清两者的根本差别：

| 维度         | 传统软件测试                          | Agent 评估                                       |
| ------------ | ------------------------------------- | ------------------------------------------------ |
| **确定性**   | 同输入必得同输出、可断言相等          | 概率性输出，同一输入多次结果不同                 |
| **任务性质** | 封闭式（close-ended），输出落在预定义值域内（如分类只有有限类别） | 开放式（open-ended），同一输入有无数种可能的正确回答 |
| **判定方式** | 有唯一/可枚举的标准答案，相等即对（可自动断言） | 无法枚举所有正确答案，只能用打分、相似度、通过率度量"好不好" |
| **评测对象** | 看单个函数的返回值                    | 看一条多步"轨迹"：规划 → 调工具 → 观察 → 再规划   |
| **失败形态** | 抛异常、返回错误值                    | 工具用错、目标跑偏、自以为完成、绕圈子……         |

**逐条展开（面试时可挑重点讲）：**

1. **确定性 → 概率性**：传统测试能写死 `assertEqual(expected, actual)`，因为同输入同输出；Agent 同一输入跑两次结果都可能不同，所以要**多次采样求统计量**（pass@k、均值、方差），单次通过不代表稳定。
2. **封闭式 → 开放式**：传统输出落在有限值域里、可枚举；Agent 面对开放任务，"合理答案"有无数种，无法穷举。
3. **等值断言 → 度量打分**：因为答案不唯一，判定方式从"相等即对"变成"用打分/相似度/裁判判好不好"，这也是从 TDD 演进到 EDD 的直接原因（呼应 1.1）。
4. **返回值 → 轨迹**：传统只看函数返回值这个"点"，Agent 要看"规划→调工具→观察→再规划"这条"线"，过程本身就是评��对象（呼应 3.4.2 轨迹评测）。
5. **异常 → 复杂失败模式**：传统失败是抛异常/错值、容易捕获；Agent 的失败更隐蔽——工具用错、目标跑偏、"自以为完成"、绕圈子，很多失败不会报错，只能靠评估发现。

**💡 一句话总结：** 传统测试问"对不对"（确定、封闭、看返回值），Agent 评估问"好不好、稳不稳、贵不贵、安不安全"（概率、开放、看轨迹）。

### 1.3 Agent 评估 5 大困境

**面试要点（对应面试卡片 Q3）：** "Agent 行业的测试面临着哪些困境？"

1. **不确定性（Non-determinism）**：同一输入多次运行结果不同，单次通过不代表稳定，需要多次采样评估分布（如 pass@k、方差）。
2. **缺乏黄金标准（No Golden Answer）**：开放任务往往没有唯一正确答案，"合理"的判定主观，难以自动化。
3. **轨迹与结果解耦（Right Answer, Wrong Reason）**：Agent 可能"蒙对"结果但过程错误（乱调工具、绕路），只看结果会漏判。
4. **评估成本高（Expensive Eval）**：跑一次完整评估集要消耗大量 Token 与时间，LLM-as-a-judge 本身也要花钱，评估的可扩展性受限。
5. **长程 & 多轮 & 多 Agent（Long-horizon / Multi-turn / Multi-agent）**：任务链路长、状态多、涉及多 Agent 协作，错误会累积传播，定位与归因困难。

**补充困境（加分项）：**
- **评估器自身不可靠**：LLM 裁判有偏见（位置偏见、长度偏见、自我偏好），需要校准。
- **分布漂移**：线上真实分布与离线评估集不一致，离线好不代表线上好。

## 二、Agent 评估全景图

### 2.1 一条主线

Agent 评估贯穿整个研发生命周期，可以用**一条主线**串起来：

```
选基模 ──→ 上线前验证 ──→ 上线后监控
  │            │                │
 选型期      组件评测          真实流量
           +系统评测          持续观测
           +发布闸门          +反馈回流
```

**主线三阶段：**
1. **选型期（选基模）**：从候选大模型中，选出最适合当前 Agent 任务的基座模型。
2. **上线前（验证）**：分层评测——先测组件（Prompt/RAG/工具/规划），再测集成系统（任务结果/轨迹/多轮/多 Agent），最后过发布闸门。
3. **上线后（监控）**：真实流量下持续观测质量、成本、安全，并把线上问题回流到评估集，形成闭环。

### 2.2 上线前验证 → 上线后监控

**面试要点（对应面试卡片 Q9）：** "你认为在 Agent 系统中，应该测试/评估哪些东西？"

**回答框架——分两大阶段，逐层展开：**

**【上线前验证】离线、可控、可回归**

| 层级       | 评测对象           | 关键问题                       |
| ---------- | ------------------ | ------------------------------ |
| 组件级     | Prompt             | 提示词是否稳定、鲁棒           |
| 组件级     | RAG / 检索         | 召回是否准、上下文是否相关     |
| 组件级     | 工具调用           | 选对工具、传对参数、结果可用   |
| 组件级     | 规划 / 推理        | 分解是否合理、步骤是否有效     |
| 系统级     | 任务结果           | 最终目标是否达成               |
| 系统级     | 轨迹               | 过程是否合理、有无冗余绕路     |
| 系统级     | 多轮交互           | 上下文保持、指代消解、纠错能力 |
| 系统级     | 多 Agent 协作      | 分工、通信、冲突解决、整体收益 |
| 闸门       | 成本/延迟/安全合规 | 是否满足发布门槛               |

**【上线后监控】在线、真实、动态**
- 真实流量质量抽检（自动+人工）
- 成本/延迟/错误率实时看板
- 安全事件（越狱、注入、有害输出）告警
- 用户反馈（点赞/点踩/重试率）回流评估集

**一句话总结：** 上线前"分层评测 + 闸门卡口"保证下限，上线后"持续监控 + 反馈闭环"保证长期质量。

## 三、评测细节

### 3.1 通用武器库

无论评测哪一层，底层都依赖三类"通用武器"：LLM-as-a-judge、比较式评估、基础度量。

#### 3.1.1 LLM-as-a-judge

> **【面试卡片】Q5：在 Agent 评测中用 LLM-as-a-judge 很火，请客观评价它的优缺点？如果由你负责实际项目落地，应该怎么科学避坑？**

**✅ 优秀回答范例：**

**【是什么】** 用一个（通常更强的）大模型，按照预先写好的评分标准（rubric）去给另一个 Agent 的输出**打分或排序**。它是目前**最主流的自动评估手段**，主流评测框架几乎无一例外都在用。

它有三种典型用法：
- **单点打分**：给一个输出打一个绝对分（如"有用性 1–5 分"）。
- **对参考打分**：把输出和"标准答案"比，判断是否一致。
- **两两比较**：给出 A、B 两个输出，让裁判选哪个更好（通常最稳，见 3.1.2）。

**【为什么测】** Agent 的输出大多是开放式自然语言，没有唯一标准答案——用精确匹配根本没法判分；纯人工评估又太慢太贵、无法规模化。LLM-as-a-judge 填补了中间地带：它能像人一样理解语义，又能像程序一样批量自动跑。《AI Engineering》给过一个有说服力的数据：**GPT-4 作为裁判与人类的一致性可达 85%，甚至高于人类评审之间的一致性（81%）**——说明在很多场景下，用强模型当裁判是可信的。

**【怎么测】** 定性地说，这是**一个方法、分 3 步走**（写标准 → 固定裁判 → 批量跑），三步是**先后顺序，不能跳**：
1. **写清楚 rubric**：定义评估维度和每个分档的含义。实战做法是借用教育学的"评分量规"概念，比如评一个推荐器，从 `subject / format / genre` 三个维度各打 1–5 分，并写明每一分代表什么。
2. **固定裁判模型和提示词**：设计模式上可用固定模型 + 低温度（如 `gemini-1.5-flash-latest`, `temperature=0.2`）搭一个专用 Judge，并用 `response_mime_type="application/json"` 强制输出 JSON 分数（含 `overall_score`、`rationale`、`detailed_feedback`、`concerns`、`recommended_action` 等字段），方便后续解析聚合。
3. **批量跑 + 聚合**：把多组输入喂进去，解析每条打分，再求平均 / 分布。

**【缺点 / 风险（面试高频）】** —— 《AI Engineering》系统揭示了裁判模型自身的三类问题，用它的时候必须警惕：

**1. 三大天生认知偏差：**
- **自我偏好偏见（self-bias）**：它会天然地给"由它自己生成的、或和它本身风格最相似"的文本打高分。用同源模型当裁判评自家模型，分数会虚高。
- **首位顺序偏差（first-position bias）**：在进行两两比较（Pairwise Match）时，如果两个模型输出质量相近，它更容易倾向于打给**第一个展示出来**的模型——顺序本身就成了干扰变量。
- **冗长语言偏差（verbosity bias）**：它是个彻头彻尾的"字数党"，往往更偏心字数巨多、排版华丽的空洞回答，哪怕短回答才是真正高密度的精确解决方案。

**2. 判分的不稳定性与无法水平度量：** 大模型对提示词极度敏感。��如 AI Engineering 揭示的那样，不同评测工具即使定义**同样的指标**（如 Faithfulness），标度却完全不一致（有 1–5 分、0/1、YES/NO）。换一个提示词或稍改下词眼，原本的 80 分就可能变成 60 分——**分数不具备像数学指标那样的绝对通用性**，只能纵向比（同一套裁判前后对比），不能跨系统横向比。

**3. 可怕的运行成本墙：** 如果每次 CI/CD 提交测试都要调用数十次 GPT-4 做 Judge，一趟迭代可能就会烧掉数千美元，最终限制了开发阶段的高频运行。所以"能用确定性指标就别用 LLM 裁判"不只是精度问题，更是成本问题。

**【科学避坑（落地实践）】** —— 真正落地时，我会严格执行以下**五条金科玉律**，把上面三类风险逐个对冲掉：

1. **Rubric 颗粒化 + Few-Shot 示例注入（治"主观/不稳定"）**：拒绝"好/中/差"或"1–5 分自拟大纲"这类模糊打分。我会把评测指标拆到具体维度（如 `Format / Subject / Relevance`），**每一档都配一条极具说服力的真实 Few-shot 对比样例**，用锚点样本引导裁判"照着样本比"，而不是凭感觉给分——这是压住判分漂移最有效的一招。

2. **CoT 分步推理 + 严格 JSON 强约束（治"随机性/幻觉打分"）**：API 里开启 `response_mime_type="application/json"`，Schema 强制包含 `rationale`（裁判思路）和 `overall_score`（综合分），并**强制"先输出理由、再输出分数"**——用思维链把打分决策显式化，既减缓裁判幻觉与随机性，又让结果可解析、可审计。

3. **洗牌（Shuffle）对抗首位/两两偏差（治"位置偏见"）**：做 Arena 两两比对时，必须让 A、B 同时跑"A 在先"和"B 在先"两轮并打乱顺序。**只有两个相反方向结论一致、或多轮均值同向胜出，才算真正胜出**，以此彻底抵消首位顺序偏差。

4. **人机偏差定量拟合 / Calibration（治"裁判不可信"）**：阶段性抽 **10%–20%** 裁判打过分的数据交给资深人类专家重评，写代码算两者的 **Cohen's Kappa 或 Pearson 相关度**；一旦拟合度低于 **0.75 立即叫停**，回去改 rubric / 提示词，直到重新校准到接近人类共识为止——把"裁判像不像人"变成一个可监控的硬指标。

5. **低温运行 + 模型平替（治"成本墙"）**：Judge 一律把 `temperature` 压到 **0.0–0.2** 的极低区间保证结果稳定；同时**不迷信 GPT-4**——日常功能迭代或简单单维度提取验证，直接换开源小模型（如 Llama-3-8B-Instruct，甚至领域蒸馏的小裁判），**用约 2% 的成本跑完 90% 的基础校验**，把昂贵闭源模型只留给关键的高价值评测。

**兜底原则（贯穿五条之上）：能用确定性指标就别用 LLM 裁判**——代码能否编译、单测是否通过、JSON schema 是否合法这类有黄金答案的，一律优先走规则/精确匹配，LLM-as-a-judge 只用在真正没有确定性答案的开放任务上。

**💡 一句话总结：** LLM-as-a-judge 是"用模型评模型"的规模化利器，能力来自语义理解、风险来自偏见与不稳定；落地靠**五条铁律**逐一对冲——**Rubric 颗粒化 + Few-shot 锚点、CoT + JSON 强约束、洗牌消位置偏差、人机 Kappa 校准（<0.75 叫停）、低温运行 + 小模型平替**，并守住"能用确定性指标就别用 LLM 裁判"的兜底原则。

#### 3.1.2 比较式评估

**是什么：** 不给绝对分，而是**两两比较**（A/B、pairwise）判断哪个更好，或对多个输出做排序。典型如 Arena（竞技场）式打榜、成对偏好标注。

**为什么有效：**
- 人和 LLM 都更擅长"比较"而非"打绝对分"，比较式判断更稳定、一致性更高。
- 天然适合无黄金答案的开放任务。
- 可用 Elo / Bradley-Terry 等模型把成对结果聚合成排名。

**适用场景：** 模型/Prompt/策略的相对优劣对比、迭代版本回归（新版本 vs 旧版本胜率）。

#### 3.1.3 基础度量：精确评估与相似度

**面试要点（对应面试卡片 Q8）：** "功能正确性、相似度、LLM-judge 三类指标怎么选？"

| 指标类型       | 代表方法                              | 适用场景                           | 特点                     |
| -------------- | ------------------------------------- | ---------------------------------- | ------------------------ |
| **功能正确性** | 单测通过、代码可编译、exact match、JSON schema 校验 | 有确定答案（代码、结构化输出）     | 客观、便宜、快，但覆盖窄 |
| **相似度**     | BLEU/ROUGE、编辑距离、Embedding 余弦相似度 | 文本生成、语义接近即可             | 半自动，抓语义但可能误判 |
| **LLM-judge**  | 大模型打分/比较                        | 开放式、需要语义与质量判断         | 灵活强大，但慢/贵/有偏   |

**选型原则（一句话）：**
> **能用精确评估就别用相似度，能用相似度就别用 LLM 裁判。** 从"确定性、便宜、可复现"往"灵活、昂贵、有偏"逐级降级，按任务是否有黄金答案来决定。

**组合使用：** 实践中往往分层组合——先用精确指标做硬门槛（如代码必须编译通过），再用相似度/LLM-judge 评质量，兼顾成本与覆盖。

### 3.2 选型期：选基模

**面试要点（对应面试卡片 Q10）：** "你是如何确定你的模型的？"

**✅ 优秀回答范例：**

我确定模型**不是看榜单排第一就用谁**，而是走 **"场景 → 能力 → 模型 → 验证"四步**，让**能力需求反过来决定该选什么模型**。下面用我做的这套 **Code Agent**（ReAct + 主从多智能体架构）串一遍。

**第一步：从业务场景反推所需能力，并配权重。** 这套 Code Agent 是 **Orchestrator（Planner）+ Sub-Agent** 的混合架构：主控负责把复杂编程需求拆成 Task DAG，子代理在沙盒里读代码、改代码、跑终端；底层还有一条"三层记忆 + 混合 RAG（BM25 + 稠密检索）"召回历史代码/决策。我把它拆成一张**可量化的能力清单并加权**：
- **代码理解与生成质量——最核心（约 30%）**：改 Bug、重构、写新特性，产出的代码要能直接用、能编译。
- **Function Calling / 工具调用——必要能力（约 25%）**：`read_file` / `edit_file` / 跑终端全靠工具调用，选错工具或参数错整条链路就断。
- **长上下文（约 20%）**：要吞下大量源码文件（"用 React 重构整个前端"这类任务）而不丢关键信息。
- **规划 / 推理（约 15%）**：Orchestrator 能把大目标拆成合理、可执行的子任务 DAG。
- **成本 / 延迟（约 10%）**：交互式编码对延迟敏感，且 Agent 会高频多轮调用，Token 成本会被放大。
- 此外**记忆那条线还要单独选一个嵌入模型**做向量检索。

**第二步：把能力画像翻译成对模型的硬性要求。** 上面的权重直接刻画出我要的"模型长相"：
1. **必须原生支持 function-calling / tools，且能稳定产出可解析的 diff / patch 与工具调用 JSON**（这是硬门槛，格式一崩整个执行编排就散架，不支持的直接出局）；
2. **代码专项能力要强**（SWE-bench / 代码修复类任务表现，而非只看通用榜单）；
3. **上下文窗口要够大**，能扛整仓库级别的代码阅读；
4. **数据合规 / 可私有化**——代码是客户核心资产，必须能私有化部署或走合规通道，不能随便外泄；
5. 是**交互式研发工具**，所以**延迟和单次调用成本要可接受**。

**第三步：据此推演该用哪一类模型（结论）。** 代码能力 + 工具调用是必要能力且要稳，所以**主控 Orchestrator/Planner 用一线、对 function-calling 支持成熟、代码能力强的旗舰模型**（Claude / GPT-4o 级 / 国内 Qwen-Max、DeepSeek-Coder 这一档都是合理候选，最终取决于成本和数据合规），负责大局规划这类高价值推理；**不拿能力不稳的小模型硬扛工具编排**。再借主从架构做**成本分层**：Sub-Agent 那些高频、相对机械的"读文件—改代码"脏活，可以下放给**性价比更高的代码专精中小模型**，只有复杂推理和跨任务编排才上旗舰模型，整体 **TCO 更优**。**嵌入模型**则按"检索质量 + 向量维度 + 成本"单独选一个主流 embedding（如 bge、text-embedding 系列）即可，**不需要和主 LLM 同源**。

**第四步：工程配置 + 验证。** 我按子任务"确定性 vs 创造性"**差异化设 temperature**：代码生成 / 工具调用参数这类要可复现、格式不能崩的用 **0～0.2**；需要一点方案发散的（如架构重构建议）才适当调高。验证上**不迷信公开榜单（SWE-bench 等也可能数据污染）**，而是**从真实仓库任务抽样建私有评测集做盲测**，重点盯几个必要能力硬指标：**任务修复成功率 / pass@k、工具调用准确率、生成 diff 的可应用率与编译/单测通过率**，达标了才定下来。

**💡 一句话收尾：** 我确定模型的逻辑是——**从 Code Agent 场景拆出带权重的能力需求 → 用必要能力（代码能力 + function-calling + 稳定结构化输出）反推出"旗舰模型做 Orchestrator 主力 + 代码专精中小模型做 Sub-Agent 分层降本 + 主流 embedding 配混合 RAG" → 再用业务私有仓库任务集盲测验证**，而不是看榜单名次直接拍板。

**加分点：** 用真实项目（主从架构的能力加权清单 + 成本分层 + 差异化 temperature + 私有仓库集盲测）说话，体现"评估集贴近业务、代码合规/成本/延迟是一等约束、按能力需求反推选型"的工程落地视角，而非唯榜单论。

### 3.3 上线前：组件评测

组件评测遵循"分而治之"：把 Agent 拆成 Prompt、RAG、工具调用、规划推理四个组件，各自独立评测，快速定位问��来源。

#### 3.3.1 Prompt 评测

**【是什么】** 评估提示词（prompt）写得好不好，以及它扛不扛攻击。

**【为什么测】** 提示词是 Agent 行为最敏感的"控制旋钮"，改一个词输出可能天差地别。但 prompt 的好坏不能靠"感觉读着顺"，得有系统化的对比；同时 prompt 还是安全攻击（越狱、注入）的主要入口，必须做防御测试。

**【怎么测】**

**定性：** 3 个相互独立的方法，分别测 prompt 的"好不好用"、"能不能自动调优"、"扛不扛攻击"——按需要取用。

- **▶ 方法一 · 质量评测：用微软 Prompt Flow 做批量对比。** 这是实战书第 9 章的主角，本身是一条分 4 步的落地流程：
  1. **【步骤】** 在 VS Code 里用 Prompt Flow（DAG 可视化流程图）搭一条评估流；
  2. **【步骤】** 用 JSONL 准备多组输入，批量跑不同的 prompt 变体（比如把参数注入到 system prompt 还是 user prompt）；
  3. **【步骤】** 用 LLM-as-judge 按 rubric 给每个变体的输出打分；
  4. **【步骤】** 用 `aggregate.py` 聚合各 run 的平均分、`log_metric` 记录指标，可视化对比哪个 prompt 更好。
- **▶ 方法二 · 自动 prompt 优化工具评测：** DSPy、TextGrad 等能自动搜索最优 prompt，但要警惕它们隐藏的 API 调用成本和模板 bug。
- **▶ 方法三 · 防御性评测：** 主动测 prompt 的鲁棒性（轻微扰动看输出是否崩）和安全性（上线前进 §3.6.3 发布闸门，上线后进 §3.7.2 持续监控）。

**落地抓手一句话：** Prompt Flow + JSONL 批处理 + LLM 打分 + 聚合对比，把"调 prompt"从玄学变成可量化实验。

#### 3.3.2 RAG / 检索评测

**面试要点（对应面试卡片 Q6）：** "评估一个 RAG 系统，你会从哪些维度入手？用什么指标？"

**✅ 优秀回答范例：**

**【是什么】** 评估 Agent 的"外挂记忆"——检索增强生成（RAG）——找回来的资料质量到底好不好。在我们这套 Code Agent 里，它就是三层记忆里那条**混合 RAG（BM25 + 稠密检索）**链路：干活前先去历史里捞相关的架构决策、踩坑记录、高频代码片段喂给模型。

**【为什么测】** RAG 是"**先检索、再生成**"的两段式流程。如果**检索**这一步捞回来的就是错的 / 不相关的，那后面**生成**得再流畅也是"一本正经地胡说八道"（幻觉）。所以 RAG 不能只看最终回答一个笼统的分，**必须拆成检索段和生成段分别评**，才能定位问题到底出在哪一段。

**【怎么测】** 我按"检索段 + 生成段"两段列考查维度，前四个是检索段、第五个是生成段，最后一条是工程上的调优抓手：

**一、检索阶段（Retrieval）——找得准不准、全不全、排得对不对：**
| 维度         | 指标                          | 含义                                   |
| ------------ | ----------------------------- | -------------------------------------- |
| 上下文精确率 | Context Precision             | 找回来的内容里，有多少是**真正相关**的 |
| 上下文召回率 | Context Recall / Recall@k     | 所有该找回的相关内容，**找回了多少**   |
| 排序质量     | NDCG、MAP、MRR                | 相关内容是否**排在前面**（越靠前越好） |
| 嵌入模型质量 | MTEB、BEIR 基准               | 你用的 **embedding 模型**本身好不好    |

**二、生成阶段（Generation）——答得实不实、切不切题：**
| 维度       | 指标                        | 含义                                     |
| ---------- | --------------------------- | ---------------------------------------- |
| 忠实度     | Faithfulness / Groundedness | 回答是否真的**"扎根"于检索到的内容**、有没有脱离资料瞎编 |
| 答案相关性 | Answer Relevance            | 回答是否切题                             |
| 正确性     | Correctness                 | 回答与标准答案是否一致                   |

**RAG Triad（经典三角）：** Context Relevance（上下文相关）、Faithfulness（忠实度）、Answer Relevance（答案相关）——三者构成 RAG 质量的核心闭环，常用 **RAGAS、TruLens** 等框架落地。

**【工程实操 · 能立刻上手调的旋钮】** 评测发现哪段差，就调对应旋钮：直接看**向量相似度分数**卡阈值、调 **top-n 召回数量**、试不同 **chunk 切分策略**、以及混合检索里 **BM25 与稠密检索的加权/重排（rerank）**，观察它们对检索精确率/召回率的影响。

**💡 记忆要点 / 一句话总结：** RAG 评测 = **检索段（precision / recall / NDCG / MRR + 嵌入模型质量）+ 生成段（faithfulness / answer relevance）两段都要测**；核心思路是**分段归因**——先看检索指标定位是"**根本没检回来**"还是"**检回来了但没用好（生成瞎编）**"，再针对性地去调 chunk、top-n、rerank 或换 embedding。

#### 3.3.3 工具调用评测

**面试要点（对应面试卡片 Q7）：** "怎么评估 Agent 的工具调用能力？它有哪几个层次？"

**✅ 优秀回答范例：**

**【是什么】** 评估 Agent 调用外部工具（API、函数、数据库）的能力——说白了就是四连问：**该不该调、选对工具没、参数填对没、结果用对没**。

**【为什么测】** 工具调用是 Agent 区别于普通聊天机器人的**核心能力**，也是**高频失败点**。它有三个不同层次，面试时能区分开会加分：
- **能力层**：在很多工具里能不能选对、调对（我们这套 Code Agent 就是几十个工具 + 依赖边构成的工具图，龙猫 VitaBench 是 66 个工具 + 512 条依赖边）；
- **行为层**：调用工具的**顺序**对不对（属于轨迹评测，见 §3.5.2）；
- **代码层**：工具函数**本身**写得对不对（单元/集成测试逐个验证 semantic function，属于传统软件测试）。

**【怎么测】** 核心思路是**"造一批考题，让 Agent 去调工具，再逐项核对它调得对不对"**。我按"由浅入深"分五层核对，前面错了后面就没意义：
1. **是否该调用（Tool Necessity）**：该调用时才调、不该调时不乱调（避免过度/遗漏调用）；
2. **选对工具（Tool Selection）**：从工具集里选出正确的那个；
3. **传对参数（Parameter Accuracy）**：参数名、类型、取值正确，格式合法（schema 校验）；
4. **结果可用与错误处理（Execution & Recovery）**：能正确解析返回值，失败时能重试或换策略；
5. **多工具编排（Orchestration）**：多步任务中调用顺序、依赖、并行是否合理（衔接轨迹评测）。

**指标示例：** 工具选择准确率、参数正确率、调用成功率、无效/冗余调用率、错误恢复率。

**【业界基准 · 借它的方法，换自己的题】** 这套方法可参考业界权威的 **Berkeley Function-Calling Leaderboard（BFCL，约 2000 道题的工具调用评测基准）**——但要注意 BFCL 属于**选型期（§3.2）**、测的是各家模型的**通用**工具调用能力，不是你自己的业务工具。真正落地要做的是**借用它的判分方法，把题目换成自己项目的工具**。

**💡 一句话总结：** 工具调用评测 = **"选对工具 ≠ 传对参数 ≠ 用对结果"**，必须**分层核对**才能精确定位到底是模型选择错、参数生成错还是编排逻辑错；造私有考题跑通"该调→选对→传对→用对→编排对"这条链路，比刷公开榜单更有说服力。

#### 3.3.4 规划 / 推理评测

**✅ 优秀回答范例：**

**【是什么】** 评估 Agent 的"**大脑**"——它能不能把一个复杂任务拆解成合理步骤、并在执行中正确推理。

**【为什么测】** 先划清和上一节的界线：**工具调用看的是"某一次调用填得对不对"（单点动作），规划/推理看的是"整条决策链对不对"（全局思路）**。一个管"手"、一个管"脑"——Agent 完全可能每一步调用都很标准，却从一开始就想错了该做什么。所以这两层必须分开评。

**【怎么测】** 核心思路是：**给 Agent 一个需要分几步才能完成的任务，记录它实际走的"步骤链"，再和"理想步骤链"对比，看它有没有想错。** 这里不抠单次调用的参数，而是看整条路对不对。我按四个维度考查，并对照《AI Engineering》总结的三类规划失败重点盯：

- **分解合理性**：复杂目标是否被拆成合理、可执行的子任务；对应失败——**"该不该用这个工具/这一步"**：在决策层选错了工具或多走了无谓的一步（注意：选哪个工具属于这里；参数填没填对归 §3.3.3）。
- **依赖正确性**：子任务顺序与依赖是否正确。
- **步骤有效性**：每一步是否推进目标，有无冗余/绕路/死循环；对应失败——**目标失败**：没达成目标，或达成了但**违反了约束**（"时间"约束最易被忽略，比如办到了营业时间之外）。
- **自我纠错**：遇阻时能否 replan（重新规划）；对应失败——**反思错误**：任务没真正完成，Agent 却**误以为完成了**就停手。

**方法：** 用带标注"理想步骤链/最优路径"的评估集比对，或用 LLM-judge 评规划质量；结合下一节的"轨迹评测"（§3.4.2）看实际执行过程。

**💡 一句话总结：** 规划评测 = 把 Agent 实际走的**步骤链**和**理想步骤链**对比，盯三类错——**选错工具/多走步、目标或约束没达成、误判已完成**；它评的是"全局路线对不对"，和工具调用评测（抠单步参数）互补而非重叠。

### 3.4 上线前·集成 / 系统评测

组件都过关，不代表系统整体行。系统评测把 Agent 当黑盒/灰盒，从端到端视角评四件事：任务结果、轨迹、多轮、多 Agent。

#### 3.4.1 任务结果评测

**✅ 优秀回答范例：**

**【是什么】** 最直接的一问：给 Agent 一个完整任务，它**最终做成了没有**。这是最贴近用户价值的指标。

**【为什么测】** 这是用户唯一真正关心的东西。但"做成没有"的**判定方式**，三份资料因**目的不同而选了不同严格度**，这点很值得讲（面试亮点）：
- **龙猫（VitaBench）**：用**全有或全无**——Pass@k / Pass^k（跑 k 次有一次成功 / 跑 k 次全成功）。因为要给模型严格**排名**，必须能拉开差距。
- **实战书**：用 **1–5 分级**（rubric 打分）。因为开发期要**诊断哪里弱**，需要颗粒度。
- **设计模式**：用**语义相似度 / 忠实度**（连续分）。因为要**持续监控漂移**，需要连续信号。

**关键认知：这不是矛盾，而是"目的决定方法"**——排名要严、诊断要细、监控要连续。用错场景（比如拿 Pass^k 做日常开发诊断）就会觉得"怎么全是 0 分"。

**【怎么测】** 判分方法不是并列可选，而是**按"你的目的"选一档严格度**：
- **档位 · 要排座次 / 狠考**：用 Pass@k / Pass^k，**温度固定**、每个任务重复多次。龙猫用 **Pass^4**（同一任务跑 4 次必须全对）来逼出模型的**稳定性**。
- **档位 · 要诊断改进**：用 **rubric 多维度 1–5 分**，看具体哪一维拉胯，便于定位优化方向。
- **档位 · 要持续监控**：用**语义相似度 / LLM-judge 连续分**，盯线上漂移。

**常用指标：** 成功率（Success Rate / Task Completion）、pass@k / pass^k、质量分（相似度或 LLM-judge）。

**⚠️ 铁律：** 因 Agent 存在不确定性，**单次成功不可信**，必须**固定温度 + 多次运行取统计量**，否则一次"蒙对"会误导结论。

**💡 一句话总结：** 任务结果评测回答"做成没有"，但**判定严格度由目的决定**——要排名用 Pass^k、要诊断用 1–5 分 rubric、要监控用连续相似度；且一律多跑几次取统计量，别信单次结果。

#### 3.4.2 轨迹评测

**面试要点（对应面试卡片 Q4）：** "一个 Agent 最终答对了，但你为什么还要看它的'轨迹'？"

**✅ 优秀回答范例：**

**【是什么】** 不只看终点，还要看 Agent **走到终点的整条路径**——它依次做了哪些动作、调了哪些工具、顺序对不对。这是设计模式书讲得最系统的部分。

**【为什么测】** 一个 Agent 可能"蒙对"了答案，但过程一塌糊涂（多绕了 10 步、调了不该调的工具）；也可能答案略有瑕疵但过程完全正确。**只看结果会误判**，轨迹评测能看出 Agent 是不是"真的会"，也能定位它在哪一步出错。具体价值有四点：
1. **防"蒙对"**：结果对但过程错（乱试、绕路、碰巧对），这种成功不可复现、不可信；
2. **成本与效率**：同样答对，用 3 步还是 30 步、花 1 万还是 10 万 Token，差别巨大；
3. **可归因 / 可调试**：轨迹暴露错误发生在哪一步（规划错？工具错？参数错？），便于定位；
4. **安全审计**：轨迹里可能藏着越权、危险操作、数据泄漏。

**【怎么测】** 这里其实是**两个独立方法**——方法一"轨迹比对"内部有 5 个由严到松的档位（按需选），方法二是实战书的"Judge-Verifier 回路"，另起一种思路：

- **▶ 方法一 · 把实际轨迹和标准轨迹（golden trajectory）做比对**，松紧分 5 档：
  - **【最严】精确匹配**：动作序列和标准轨迹完全一致；
  - **【按序匹配 in-order】**：关键动作按正确顺序出现即可，允许中间有别的；
  - **【任意顺序 any-order】**：关键动作都出现就行，不计顺序；
  - **【精确率 / 召回率】**：实际动作里有多少是该做的、该做的又做了多少；
  - **【最细】单一工具使用**：单独看某个关键工具用得对不对。
- **▶ 方法二 · Judge-Verifier 回路**：实战书第 6 章用行为树搭了"Hacker→Judge→Verifier"三段式——Judge Agent 评判解答，Verifier Agent 在独立线程里**真的把代码跑一遍**做二次验证。这是"轨迹 + 结果"双重把关的好例子。

**轨迹还常评：** 步骤数 / 冗余步骤（效率）、是否偏离最优路径、有无死循环或反复试错。

**💡 一句话总结：** 只看结果是"结果论"，看轨迹才能判断这次成功是否**可靠、高效、可复现**；落地上用"实际轨迹 vs golden 轨迹"5 档比对（要严用精确匹配、要宽松用 any-order），关键场景再叠一层 Judge-Verifier 真跑验证。

#### 3.4.3 多轮交互评测

**✅ 优秀回答范例：**

**【是什么】** 评估 Agent 在**多轮对话**中的表现——用户会追问、改主意、说得含糊，Agent 能不能跟得住。这是龙猫（VitaBench）几乎**独家深入**的领域。

**【为什么测】** 真实用户不会一次把需求说全。前面的组件评测、单轮评测都假设"一问一答"，但实际场景是"**边聊边改**"。如果不专门测多轮，上线后才会发现 Agent 一到真实对话就乱套。

**【怎么测】** 这是**一套完整流程**，不是几种方法任选。核心是：**固定"环境 + 隐藏用户目标 + 评分 Rubric"，让用户模拟器动态生成多轮对话，被测 Agent 正常应对，最后用终态 + Rubric 判断任务是否完成。**

**第一步：制作多轮评测数据集——但不是写死对话文本。** 样本不是"用户问一句、标准答案一句"，而是一个**任务包**，含三件固定内容（示例）：

```json
{
  "environment": {                          // 客观世界：菜单/库存/价格/时间槽
    "restaurant": "川味小馆",
    "menu": [
      {"name": "麻婆豆腐", "price": 38, "stock": 5},
      {"name": "水煮鱼", "price": 88, "stock": 2}
    ],
    "delivery_slots": ["18:30", "19:00", "19:30"]
  },
  "user_goal_card": {                        // 隐藏用户目标：Agent 看不到
    "hidden_goal": "点一份麻婆豆腐",
    "budget": "不超过50元",
    "delivery_time": "19:00前送达",
    "dynamic_change": "中途把'微辣'改成'不辣'"   // 模拟改主意
  },
  "rubric": [                                // 评分标准：只给判分器
    "最终商品必须是麻婆豆腐",
    "口味必须是不辣",
    "金额不能超过50元",
    "送达时间不能晚于19:00",
    "下单前必须向用户复述确认"
  ]
}
```

**关键在于分清三份信息给谁看：**
- **environment（环境/后台状态）**：被测 Agent、用户模拟器、判分器**都可见**，提供菜单、库存、价格、时间槽等客观世界；
- **user_goal_card（隐藏用户目标）**：**只给用户模拟器**，是用户"心里想的"，Agent 看不到，只能靠追问和推荐去摸；
- **rubric（评分标准）**：**只给判分器**，规定最后怎么判 Pass / Fail。

被测 Agent **看不到隐藏目标卡，也看不到 Rubric**——它只能像真实线上一样，根据用户模拟器一句句说出来的话去追问、推荐、调用工具、确认、下单。

**第二步：运行时动态多轮对话。** 用户模拟器拿着隐藏目标卡，一句句抛需求（"想点个下饭的，别太贵" → "微辣……等下改不辣，19 点前到"），Agent 只凭对话和环境工具应对，中途还要处理"改口"。

**第三步：终态 + Rubric 双通道判分**（不比对话文本，只看终态和关键行为是否满足 Rubric）：
- **通道① 代码 assert（结构化终态）**：商品=麻婆豆腐、口味=不辣、金额≤50、送达≤19:00，硬校验；
- **通道② LLM Judge（语义行为）**：是否处理了改口、下单前是否复述确认、有没有擅自臆测。

**评什么（能力维度）：** 上下文保持、指代消解（"它/那个/上一步"）、纠错能力（用户改口后能否修正而非重复犯错）、目标漂移（多轮后是否偏离原始目标）。

**稳定性：Pass^4。** 同一任务包动态跑 4 次（说法和改口时机可不同），**全部通过才算稳定**——防止蒙对，逼出鲁棒性。

**💡 一句话总结：** 多轮评测 = **固定环境 + 隐藏目标 + Rubric，用户模拟器动态生成对话，最后按终态判分（代码 assert + LLM Judge 双通道）**；固定的是环境/目标/评分标准而**不是对话文本**，再用 Pass^4 逼出稳定性。

#### 3.4.4 多 Agent 协作评测

**面试要点（对应面试卡片 Q11）：** "多 Agent 系统中，你应该如何评估多个 Agent 之间的协作？"

**✅ 优秀回答范例：**

**【是什么】** 当系统由多个 Agent 组队完成任务时，评估这个"**团队**"协作得好不好。

**【为什么测】** 多 Agent 系统多出一层全新的失败面——它们之间会不会有效协作、有没有选对该干活的 Agent、加 Agent 到底是帮忙还是添乱。**单 Agent 的指标测不出这些"团队动态"**，所以我不会只看最终任务完没完成，而是从三层来评。

**【怎么测】** "协作好不好"**不要抽象地打一个总分，而要拆成三套可执行测法**（可叠加使用）。先给个具体场景：假设智能预约系统有 4 个 Agent——`Router`（判断意图、决定交给谁）、`Calendar`（查档期）、`Weather`（查天气）、`Booking`（最终下单）：

**第一层 · 交接轨迹评测（团队配合有没有走对）。** 为每条任务定义**标准协作链**，记录真实运行 trace，检查是否选对 Agent、是否传对关键字段、交接顺序是否合理、最终状态是否正确。一条测试任务可写成：

```json
{
  "task": "帮我约明天下午2点的精油按摩，如果明天下雨就改到后天",
  "expected_handoffs": [
    "Router -> Weather Agent(date=明天)",
    "Weather Agent -> Router(result=rain)",
    "Router -> Calendar Agent(date=后天, time=14:00)",
    "Calendar Agent -> Booking Agent(slot=后天14:00)"
  ],
  "expected_final_state": {
    "booking_date": "后天",
    "booking_time": "14:00",
    "service": "精油按摩"
  }
}
```

**第二层 · 消融评测（某个 Agent 有没有真实贡献）。** 固定同一批 evalset，分别跑 **Full Team / 去掉某个 Agent / 退化成 Single Agent** 等版本，比较端到端成功率、成本、延迟和错误类型：
- 加了 `Weather` 后成功率只提升一点点、但 token 翻倍 → 它可能**不值得**（过度设计）；
- 去掉 `Router` 后误调工具率大幅上升 → 说明 `Router` 是**必要组件**。

**第三层 · 过程监控 + 质检 Agent（协作过程为什么慢、贵、乱，瓶颈在哪）。** 用 trace / AgentOps 记录每个 Agent 的输入、输出、耗时、token、调用次数，再让 **Reviewer / Critic Agent** 检查中间状态，抓重复调用、无效交接、状态冲突、过早下单、该人工兜底却没兜底等问题。

**其它评估维度（可并入上述三层）：** 分工合理性（有无重叠/遗漏）、通信质量（信息传递准确无损）、冲突解决（能否收敛不僵局）、错误传播（单点出错是否被放大传染）。

**💡 一句话总结：** 多 Agent 协作评测 = **交接链是否正确（第一层）+ 增加 Agent 是否有边际收益（第二层）+ 协作过程是否健康（第三层）**。最终报告我会同时给出端到端成功率、交接正确率、Agent 选择正确率、消融收益、token/latency 成本以及主要失败类型——而不是拍脑袋打一个"协作 8 分"。

### 3.5 上线前收口：Pipeline 与发布闸门

组件和系统评测的结果，最终要收口成一个**自动化 Pipeline** 和一道**发布闸门（Release Gate）**，决定这个版本能不能上线。

#### 3.5.1 发布闸门卡什么

发布闸门就是一组**硬性阈值**，CI/CD 中自动跑评估集，不达标就阻断发布：
- **质量门槛**：任务成功率 ≥ 阈值、关键用例 100% 通过、无质量回归。
- **回归检查**：新版本在核心评估集上不能比旧版本差（胜率/分数）。
- **成本/延迟门槛**：见 3.5.2。
- **安全门槛**：见 3.5.3。

#### 3.5.2 成本、效率、延迟

作为一等指标纳入闸门：
- **成本**：平均任务 Token 消耗、单位成本，超预算阻断。
- **效率**：平均步骤数、工具调用次数。
- **延迟**：P50/P95/P99 端到端耗时、首 Token 延迟。

**要点：** 质量提升若以成本/延迟大幅恶化为代价，需权衡；闸门帮你量化这个权衡。

#### 3.5.3 安全与合规

**面试要点（对应面试卡片 Q13）：** "你会怎么评估 Agent 的安全性？"

**评估维度：**
1. **提示注入 / 越狱（Prompt Injection / Jailbreak）**：用红队用例集测试能否被诱导绕过安全策略、执行恶意指令。
2. **有害输出（Harmful Content）**：是否产出违法、有害、歧视内容。
3. **数据泄漏（Data Leakage）**：是否泄漏系统提示、隐私数据、密钥。
4. **越权操作（Unauthorized Action）**：工具调用是否越界（如删库、越权访问）。
5. **合规**：是否满足数据合规、审计留痕要求。

**方法：**
- **红队评估集（Red-teaming）**：专门构造攻击用例集，持续跑分。
- **护栏（Guardrails）**：输入/输出过滤、工具权限白名单、沙箱执行。
- **审计日志**：全链路留痕，便于事后追溯。

**加分点：** 强调安全是"攻防对抗、持续演进"，红队集要不断更新，不能一次评估就了事。

### 3.6 上线后监控

**面试要点（对应面试卡片 Q12）：** "你的项目上线以后，你如何保证和监测上线质量？"

**回答框架——上线不是终点，而是持续评估的起点：**

1. **实时监控看板**：成功率、错误率、成本、延迟（P95/P99）、工具调用异常率实时可视化，异常告警。
2. **质量抽检**：对真实流量做自动评估（LLM-judge）+ 人工抽样标注，监测质量漂移。
3. **用户反馈信号**：点赞/点踩、重试率、会话中断率、人工接管率，作为质量代理指标。
4. **安全监控**：越狱/注入/有害输出实时检测与告警。
5. **反馈闭环（关键）**：把线上失败案例、用户点踩样本回流，**补充进离线评估集**，驱动下一轮迭代——形成"上线→监控→回流→再评估→再上线"闭环。
6. **A/B & 灰度**：新版本先灰度，用线上指标对比再全量。

**一句话总结：** 离线评估保下限，线上监控保长期，反馈回流让评估集越用越强，这是 EDD 闭环的落地。

## 四、实战：美团 LongCat VitaBench

**面试要点（对应面试卡片 Q14）：** "介绍一个你了解的 Agent 评测 benchmark，它是怎么设计的？"

VitaBench 是美团 LongCat 团队提出的、面向真实复杂交互场景的 Agent 评测基准，代表了"贴近真实业务"的评测设计思路。

### 4.1 整体思想

- **面向真实场景**：不用玩具任务，而是构造贴近真实生活服务（如点餐、出行、预订等复杂多步交互）的场景，考察 Agent 在真实业务中的综合能力。
- **多轮 + 多工具 + 长程**：任务需要多轮交互、调用多个工具、跨多步完成，综合考察规划、工具调用、上下文保持能力。
- **可组合、可扩展**：场景与工具解耦，能灵活组合出多样任务，避免模型"背题"。
- **结果 + 过程双评**：不仅看任务是否完成（结果），也评估交互轨迹是否合理（过程），对应前文"轨迹评测"思想。
- **贴近工业落地**：把成本、效率、稳定性等工程指标纳入考量，而非纯学术精度。

### 4.2 结果与启示

**启示（面试可讲的结论）：**
1. **真实复杂任务是试金石**：模型在简单基准上分数高，不代表能扛真实多轮多工具任务，复杂交互下成功率显著下降。
2. **过程评估不可省**：结果对不等于过程对，轨迹评测能揭示"蒙对"和低效路径。
3. **评测集要贴业务**：好的 benchmark 一定是从真实场景抽象而来，这也印证了 3.2 节"选基模要用业务私有数据集"的观点。
4. **综合能力 > 单点能力**：Agent 评测考的是规划、工具、记忆、纠错的综合协同，任何单点短板都会暴露在长程任务里。

**引用价值：** 面试时用 VitaBench 佐证你对"真实场景评测、结果+过程双评、工程指标纳入"的理解，比空谈指标更有说服力。
